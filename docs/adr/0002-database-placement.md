# ADR-0002. Размещение базы данных

- Статус: принято
- Дата: 2026-10-01

## Контекст

В ЛР2 приложение TimeCapsule и PostgreSQL работали на одном экземпляре EC2 в default VPC.
Теперь у приложения своя сеть `timecapsule-dev-vpc` (`10.17.0.0/16`) с публичными и приватными подсетями
в двух зонах доступности. Нужно решить, где разместить базу данных.

Требования и ограничения:

- к базе не должно быть пути из интернета, даже если ошибиться в одном из фильтров;
- приложение должно находить базу по стабильному имени, а не по адресу;
- базе нужны обновления безопасности, хотя постоянный выход в интернет ей не нужен;
- один студент и бюджет в несколько долларов, поэтому лишние почасовые ресурсы недопустимы.

## Решение

База работает на отдельном экземпляре `timecapsule-dev-db` в приватной подсети `timecapsule-dev-private-a`
(`10.17.10.0/24`), без публичного адреса и без маршрута в Internet Gateway.

- Подключиться к порту 5432 можно только из группы `timecapsule-dev-web-sg` (правило в `timecapsule-dev-db-sg`).
  В `pg_hba.conf` разрешён вход только пользователю `timecapsule` в базу `timecapsule` из подсети `public-a`.
- SSH на `db-server` разрешён только из `timecapsule-dev-bastion-sg`, то есть через bastion.
- Приложение обращается к базе по имени `db.timecapsule.internal` из приватной зоны Route 53,
  которая видна только внутри VPC.
- Обновления ставятся через временный NAT Gateway. Его поднимает `scripts/nat-up.sh`, удаляет `scripts/nat-down.sh`.

## Рассмотренные альтернативы

- **На одном сервере с приложением (как в ЛР2).** Самый дешёвый вариант: нет лишнего экземпляра и сетевых задержек,
  база слушает только `localhost`. Но приложение и база делят процессор, память и диск, а взлом приложения даёт доступ к базе
  на той же машине. Данные привязаны к одному серверу, поэтому приложение нельзя запустить во втором экземпляре,
  а потеря сервера означает потерю и кода, и данных. Отказались.
- **Отдельный сервер в публичной подсети.** Обновления ставятся напрямую, NAT не нужен. Но у базы появляется публичный адрес
  и маршрут в интернет: от доступа из интернета её отделяют только Security Group и `pg_hba.conf`, и одна ошибка в любом из них
  открывает базу миру. К публичным адресам постоянно подбирают пароли. Отказались.
- **Отдельный сервер в приватной подсети (выбрано).** Доступ защищают три независимых механизма: отсутствие публичного адреса
  и маршрута, Security Group и `pg_hba.conf`. Ошибка в одном из них не открывает базу из интернета.

## Последствия

- Плюс: база недоступна из интернета, а приложение и данные можно развивать независимо: сервер приложения можно пересоздать,
  не трогая данные. Смена адреса `db-server` сводится к правке одной записи в Route 53.
- Плюс: проверено на практике. При остановке `db-server` приложение вернуло ошибку и `"db":"error"` в `/health`,
  а после запуска базы снова заработало без изменений на `app-server`, потому что приватный адрес сервера не меняется.
- Как база получает обновления без постоянного выхода в интернет: на время установки поднимается NAT Gateway,
  затем он удаляется. Скрипты `nat-up.sh` и `nat-down.sh` делают это воспроизводимо за несколько минут, включая выделение
  и освобождение Elastic IP. Забытый NAT Gateway стоит около $1,25 в сутки, а при использовании по несколько минут
  обходится в центы. Платить за него постоянно ради редких обновлений нецелесообразно.
- Почему у `app-server` Elastic IP: публичный адрес обычного экземпляра меняется при каждой остановке и запуске,
  и пришлось бы каждый раз править `APP_URL` и адрес в браузере. Elastic IP закрепляет за сервером постоянный адрес.
  Он стоит около $0,005 в час всегда, даже у остановленного сервера (примерно $3,6 в месяц).
  Когда перед `app-server` появится балансировщик нагрузки, пользователи будут приходить на его DNS-имя,
  а сам `app-server` можно будет перенести в приватную подсеть. Тогда Elastic IP на нём станет не нужен.
- Минус: один экземпляр базы в одной зоне доступности (`private-a`) без репликации и автоматических резервных копий.
  Отказ зоны `a` остановит и базу, и приложение. Подсеть `private-b` пока пуста и подготовлена для реплики или восстановления.
- Минус: трафик между приложением и базой внутри VPC не шифруется, защищает только аутентификация `scram-sha-256`.
- Минус: лишний почасовой экземпляр и необходимость вручную обновлять его через временный NAT Gateway.
