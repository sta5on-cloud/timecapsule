# ADR-0001. Способ доставки кода на сервер

- Статус: принято
- Дата: 2026-10-01

## Контекст

TimeCapsule работает на одном экземпляре EC2 (Amazon Linux 2023): nginx, PHP-FPM и
PostgreSQL на одной машине. Новые версии приложения нужно выкладывать на сервер,
и к способу доставки есть требования:

- понятно, какая версия кода сейчас работает на сервере;
- если версия оказалась с ошибкой, можно быстро вернуть предыдущую;
- нельзя потерять данные, которые живут только на сервере: файл `.env` с паролем
  к базе, папку `storage/` с загруженными файлами и саму базу данных;
- процесс должен выполняться одинаково каждый раз, независимо от того, кто и когда его запускает.

Ограничения: один сервер, один разработчик, публичный репозиторий на GitHub,
системы CI/CD в курсе пока не проходили.

## Решение

Единственным источником кода является репозиторий GitHub. Сервер сам забирает из него
код по HTTPS командой `git pull --ff-only`. Все шаги выпуска записаны в скрипте
`~/deploy.sh` на сервере:

1. `git pull --ff-only`
2. `composer install --no-dev --optimize-autoloader --no-interaction`
3. `php bin/init-db.php`
4. `sudo systemctl reload php-fpm`

Деплой запускается с компьютера разработчика одной командой:
`ssh -i <ключ> ec2-user@<IP> ./deploy.sh`.

Откат выполняется через репозиторий: `git revert --no-edit HEAD`, `git push` и повторный деплой.
Править код прямо на сервере нельзя.

## Рассмотренные альтернативы

- **Копирование через `scp`.** Самый простой способ, но у него нет версий: нельзя сказать,
  какой код работает на сервере. Легко забыть скопировать один файл или скопировать
  лишнее (`.env`, `vendor/`). Откатиться можно только вручную, "как-нибудь", потому что
  предыдущей версии нигде нет. Код живёт на ноутбуке, а не в общем месте. Отказались.
- **`git pull` вручную на сервере.** Версия и откат решаются через git, но порядок
  команд (`git pull`, `composer install`, `init-db.php`, `reload php-fpm`) приходится
  помнить и вводить каждый раз. Достаточно пропустить `composer install` или `reload`, и
  сайт сломается или останется на старом коде. Результат зависит от внимательности
  человека. Подходит как запасной вариант, но не как основной процесс.
- **Скрипт `deploy.sh` (выбрано).** Те же команды, что и при ручном варианте, но в одном
  файле. `set -euo pipefail` останавливает выпуск при первой ошибке, `--ff-only` не даёт
  смешать чужие правки на сервере с новым кодом, а последняя строка вывода показывает,
  какой коммит теперь работает.
- **CI/CD (например, GitHub Actions).** Автоматически проверял бы и выкладывал код после
  каждого `git push`. Сейчас избыточно для одного сервера и не входит в изученное,
  но `deploy.sh` устроен так же, и его можно позже вызвать из CI/CD без изменений.

## Последствия

- Плюс: процесс выпуска воспроизводим, версия на сервере видна по последнему коммиту,
  данные сервера (`.env`, `storage/`, база) не затрагиваются, потому что `.env`
  и `storage/uploads` не отслеживаются git.
- Плюс: откат быстрый и сохраняет историю. При проверке сломанный коммит был откачен
  и выложен примерно за 5 секунд работы, а капсула с файлом осталась на месте.
- Минус: перед выкладкой нет автоматических проверок. Коммит с синтаксической ошибкой
  дошёл до сервера, и главная страница вернула 500, хотя `/health` продолжал отвечать `ok`,
  потому что проверяет только PHP и базу, но не отображение страниц.
- Минус: `git pull` заменяет файлы по одному, поэтому в течение нескольких секунд
  посетитель может увидеть смесь старой и новой версий. Атомарного переключения нет.
- Минус: скрипт `deploy.sh` лежит на сервере, а не в репозитории, поэтому сам не версионируется.
- Риск: единственный сервер остаётся единой точкой отказа, а доступ по SSH зависит от
  ключа и правила Security Group для IP разработчика.
- Улучшения позже: проверка кода до деплоя (`php -l`, тесты), проверка главной страницы
  после деплоя с автоматическим откатом, выкладка в новую папку с переключением симлинка,
  перенос шагов в CI/CD.
