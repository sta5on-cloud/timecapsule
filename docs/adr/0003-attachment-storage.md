# ADR-0003. Где хранить вложения пользователей

- Статус: принято
- Дата: 2026-10-29

## Контекст

В ЛР2 и ЛР3 вложения капсул (картинки и PDF) лежали в папке `storage/uploads` на диске EBS сервера `app-server`.
Приложение само читало файл с диска и отдавало его браузеру. Пока сервер один, это работает, но у такого
хранения есть проблемы:

- данные пользователей живут только на одном сервере: при его замене или потере пропадают все вложения;
- второй сервер приложения рядом не запустить: он не увидит файлы первого;
- каждый файл проходит через PHP-FPM и занимает процесс приложения на всё время скачивания;
- от случайного удаления файла защищают только снимки EBS, которые никто не делает.

Требования:

- вложения не должны зависеть от конкретного сервера приложения;
- посторонний не должен получить файл, даже зная его имя; проверка прав остаётся в приложении;
- случайное удаление можно отменить, а стоимость хранения не растёт бесконечно;
- никаких постоянных ключей доступа в `.env` и в публичном репозитории;
- бюджет в несколько долларов, без новых почасовых ресурсов.

## Решение

Вложения хранятся в бакете Amazon S3 `timecapsule-dev-uploads-sta5on` (регион `eu-north-1`, как и сервер),
под префиксом `uploads/`. Модуль `src/storage.php` работает только с S3 через AWS SDK for PHP:

- `storage_save()` загружает файл командой `PutObject` под ключом `uploads/<случайное имя>` с правильным `Content-Type`;
- `storage_delete()` вызывает `DeleteObject`;
- `storage_stream()` не отдаёт файл сам, а возвращает браузеру `302` на подписанный URL `GetObject` сроком 5 минут.
  В подпись входят `response-content-type` и `response-content-disposition`, поэтому S3 отдаёт файл с исходным именем
  и нужным способом показа (`inline` или `attachment`).

Настройки бакета: `Block all public access`, `ACLs disabled`, шифрование `SSE-S3`, политика бакета запрещает запросы
без HTTPS, включено версионирование, правило жизненного цикла `timecapsule-dev-noncurrent`.

Права приложения задаёт роль `timecapsule-dev-app-role`, привязанная к `app-server`. Её политика `timecapsule-dev-app-s3`
разрешает только `s3:GetObject`, `s3:PutObject` и `s3:DeleteObject` на `uploads/*`. После переноса старых файлов
правило с `s3:ListBucket` убрано: приложению список объектов не нужен.

## Рассмотренные альтернативы

- **Диск EBS сервера приложения (как в ЛР2 и ЛР3).** Самый простой вариант, без новых сервисов и кода. Но диск
  привязан к одному экземпляру в одной зоне доступности: второй сервер его не видит, а при замене сервера файлы нужно
  переносить вручную. Файлы отдаёт PHP, защиту от удаления дают только снимки EBS. Отказались.
- **Общая файловая система Amazon EFS.** Её можно смонтировать на несколько серверов в разных зонах, код приложения
  почти не меняется (тот же `storage/uploads`). Но EFS живёт внутри VPC, нужны mount target в каждой зоне и правила
  NFS в Security Group, а файлы всё равно отдаёт PHP через сервер приложения. Стоит дороже S3 за гигабайт,
  а отменить удаление файла средствами самой EFS нельзя, только через AWS Backup. Отказались.
- **Бакет Amazon S3 (выбрано).** Хранилище вне VPC и вне серверов, доступное из любой зоны и с любого сервера по API.
  Браузер скачивает файл напрямую из S3, не нагружая приложение. Версионирование и жизненный цикл встроены,
  доступ без ключей через роль EC2. Минус: нужно переписать модуль хранения и подключить SDK.

## Последствия

- Как пользователь получает файл. Браузер запрашивает `/capsules/{id}/file`, приложение проверяет, что пользователь
  может видеть капсулу и что она уже открыта, и отвечает `302` на подписанный URL. Браузер скачивает файл напрямую
  из S3. Ссылку ограничивают срок `X-Amz-Expires=300` (5 минут) и срок временных учётных данных роли, которыми она
  подписана: после него ссылка перестаёт работать, даже если 5 минут не прошли. Изменить ключ, тип или имя файла
  в ссылке нельзя: подпись перестанет совпадать (`SignatureDoesNotMatch`). Отзывать пересланную ссылку не нужно,
  она истекает сама.
- Что защищает файлы от случайного удаления. При включённом версионировании `DeleteObject` только ставит маркер
  удаления, а старая версия остаётся и её можно вернуть, удалив маркер. Политика приложения не даёт
  `s3:DeleteObjectVersion` и `s3:ListBucketVersions`, поэтому даже с украденными учётными данными сервера нельзя
  уничтожить историю версий.
- Что ограничивает рост стоимости. Правило `timecapsule-dev-noncurrent` для `uploads/` переводит неактуальные версии
  в Standard-IA через 30 дней и удаляет их через 90 дней, оставляя две последние, а незавершённые multipart-загрузки
  удаляет через 7 дней. Файлы меньше 128 КБ в Standard-IA не переходят: для них это дороже.
- Минус: у вложения удалённой капсулы одна неактуальная версия, и она попадает в «две последние», которые правило
  сохраняет, поэтому такие версии не удаляются сами. Пока данных мало, это допустимо; если удалённые вложения должны
  исчезать, нужно отдельное правило без `NewerNoncurrentVersions` и с удалением просроченных маркеров.
- На сервере приложения не осталось данных пользователей, только код и настройки. Это проверено: папка
  `storage/uploads` удалена, старые и новые капсулы открываются. Заменить `app-server` можно новым сервером из образа
  или из репозитория, привязав к нему ту же роль.
- Что изменится с несколькими серверами и балансировщиком. Все серверы получают одну роль `timecapsule-dev-app-role`
  и пишут в один бакет, поэтому файл, загруженный через один сервер, сразу доступен через другой. Балансировщику
  не нужна привязка пользователя к серверу из-за файлов, а скачивания идут мимо балансировщика и серверов, напрямую
  из S3. Сессии в `storage/sessions` всё ещё лежат на диске, их придётся вынести (например, в базу или ElastiCache),
  это отдельное решение.
- Минус: бакет в одном регионе. Отказ всего `eu-north-1` сделает вложения недоступными. Для защиты нужна
  репликация бакета в другой регион (Cross-Region Replication), это удвоит стоимость хранения.
- Минус: появилась внешняя зависимость. Без доступа к S3 (ошибка роли, политики или сети) капсулы с вложениями
  не создаются и не открываются. Ошибки видны в журнале PHP-FPM.
