# ADR-0005. Где хранить сессии пользователей

- Статус: принято
- Дата: 2026-11-18

## Контекст

До ЛР6 TimeCapsule работал на одном сервере `app-server`, а PHP хранил сессии файлами в `storage/sessions/`
на его диске. В ЛР6 приложение запускается в группе Auto Scaling `timecapsule-dev-asg` за балансировщиком
`timecapsule-dev-alb`: серверов от двух до четырёх, они появляются и исчезают сами, запросы одного пользователя
балансировщик раздаёт разным серверам. Файл сессии, созданный на одном сервере, другой сервер не видит, и
пользователь, который вошёл, на следующем запросе оказывается не залогинен.

Требования:

- вход сохраняется, на какой бы сервер ни попал запрос, в том числе когда группа добавляет или удаляет серверы,
  заменяет неисправный или выпускается новая версия (новый образ);
- серверы взаимозаменяемы: на диске сервера нет ничего, что жалко потерять;
- нет ключей доступа в `.env`, права выдаются ролью `timecapsule-dev-app-role`;
- старые сессии удаляются сами;
- минимум нового кода и расходы студенческого стенда;
- локальная разработка в Docker продолжает работать без AWS.

## Решение

Сессии хранятся в таблице Amazon DynamoDB `timecapsule-dev-sessions`:

- ключ раздела `id` (String), режим `On-demand`, TTL по атрибуту `expires`;
- приложение (`open_capsules_php_functional`) в `start_session()` регистрирует готовый обработчик из AWS SDK
  `Aws\DynamoDb\SessionHandler::fromClient(...)` с `table_name` из `SESSIONS_TABLE` в `.env`; если переменная
  пустая (локальный Docker), сессии по-прежнему лежат в файлах;
- SDK берёт временные учётные данные роли сервера; политика `timecapsule-dev-app-sessions` разрешает только
  `GetItem`, `PutItem`, `UpdateItem` и `DeleteItem` на эту одну таблицу;
- привязка сессий к серверу (stickiness) в целевой группе выключена.

## Рассмотренные альтернативы

| Вариант | Что меняется в коде | Что теряется при замене сервера | Удаление старых сессий | Цена для стенда |
| --- | --- | --- | --- | --- |
| Файлы + sticky sessions на ALB | ничего | все сессии этого сервера | GC PHP на каждом сервере | бесплатно |
| Таблица `sessions` в RDS | свой `SessionHandlerInterface`, таблица, миграция | ничего | своя задача `DELETE ... WHERE expires < now()` | бесплатно, но нагрузка на `db.t4g.micro` |
| DynamoDB (выбрано) | 3 строки: регистрация обработчика из SDK | ничего | TTL DynamoDB | доли цента в месяц |

- **Файлы на сервере и sticky sessions.** Балансировщик ставит cookie `AWSALB` и шлёт пользователя на тот же сервер.
  Код менять не надо, но сессия по-прежнему живёт на одном сервере: при уменьшении группы, замене неисправного
  сервера или выпуске нового образа пользователи этого сервера разлогиниваются. Нагрузка распределяется неравномерно:
  новые серверы, которые группа запустила под нагрузкой, получают только новых пользователей, а «привязанные»
  остаются на старых. Это противоречит идее взаимозаменяемых серверов. Отказались.
- **Таблица в RDS.** Данные уже в PostgreSQL, новый сервис не нужен. Но для PHP без фреймворка готового
  обработчика нет: нужно написать свой класс с блокировками, таблицу и периодическую очистку. Каждый запрос
  пишет в базу (обновление времени сессии), а `db.t4g.micro` - единственный и самый слабый узел системы.
  Вход начинает зависеть от базы, которая к тому же ночью останавливается по расписанию. Отказались.
- **DynamoDB (выбрано).** Готовый обработчик в AWS SDK, который уже подключён для S3 (ЛР4). Таблица без серверов,
  доступна из всех зон региона, не останавливается и не требует обслуживания. Старые сессии удаляет TTL.
  Платим только за запросы: несколько тысяч учебных запросов стоят доли цента.

## Последствия

- Серверы приложения не хранят ничего своего: код и `.env` приходят из образа, вложения из S3, данные из RDS,
  сессии из DynamoDB. Любой сервер группы обслуживает любой запрос, поэтому группа может свободно добавлять,
  удалять и заменять серверы, а sticky sessions не нужны.
- Каждый запрос с сессией делает чтение и запись в DynamoDB (несколько миллисекунд внутри региона). При
  недоступности DynamoDB или ошибке прав (`AccessDeniedException`) вход перестаёт работать на всех серверах сразу.
- Обработчик по умолчанию работает без блокировок: при двух одновременных запросах одной сессии побеждает последняя
  запись. Для TimeCapsule (сессия хранит только id пользователя и CSRF-токен) это допустимо.
- TTL удаляет просроченные элементы не мгновенно, а в течение примерно двух суток; обработчик сам не возвращает
  сессию, у которой истёк `expires`, поэтому на безопасность это не влияет.
- Появилась ещё одна зависимость от AWS (переход к другому провайдеру потребует другого хранилища), её
  смягчает то, что выбор хранилища - одна функция `start_session()`, а локально остаются файлы.
- Образ сервера нужно создавать только после выпуска версии с DynamoDB, иначе новые серверы будут хранить сессии
  в файлах, и вход снова начнёт теряться.
