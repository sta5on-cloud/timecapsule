### Задание 1. План адресов

| Подсеть     | Зона доступности | Диапазон        | Первый и последний адрес, доступный экземплярам | Сколько адресов доступно экземплярам |
| ----------- | ---------------- | --------------- | ----------------------------------------------- | ------------------------------------ |
| `public-a`  | `eu-north-1a`    | `10.17.0.0/24`  | `10.17.0.4` - `10.17.0.254`                     | 251                                  |
| `public-b`  | `eu-north-1b`    | `10.17.1.0/24`  | `10.17.1.4` - `10.17.1.254`                     | 251                                  |
| `private-a` | `eu-north-1a`    | `10.17.10.0/24` | `10.17.10.4` - `10.17.10.254`                   | 251                                  |
| `private-b` | `eu-north-1b`    | `10.17.11.0/24` | `10.17.11.4` - `10.17.11.254`                   | 251                                  |

**Почему доступных адресов не 256? Какие адреса подсети `10.X.0.0/24` занимает AWS и для чего? Сколько ещё подсетей `/24` поместится в вашу VPC?**
AWS резервирует в каждой подсети пять адресов: `.0` - адрес сети, `.1` - виртуальный маршрутизатор VPC, `.2` - DNS-сервер VPC, `.3` - резерв на будущее, `.255` - широковещательный адрес (в VPC не поддерживается, но тоже зарезервирован). Поэтому из 256 адресов остаётся 251. В VPC `/16` помещается 256 подсетей `/24`, четыре уже созданы, значит можно добавить ещё 252.

### Задание 2. VPC и подсети

**Является ли подсеть `public-a` сейчас публичной? Почему?**
Нет. Публичной подсеть делает не название, а маршрут `0.0.0.0/0` в Internet Gateway. Сразу после создания подсеть связана с основной таблицей маршрутов, где есть только локальный маршрут VPC, поэтому выхода в интернет у неё ещё нет.

![Страница web-server](screenshots/task5-web-server-page.png)

Страница `web-server` в браузере: имя сервера и его приватный адрес `10.17.0.68` из подсети `10.17.0.0/24`.

![Зависшая установка на db-server](screenshots/task5-db-dnf-hang.png)

На `db-server` (подключение `ssh db` через bastion) установка `postgresql16-server` зависает: репозиторий недоступен, после `Ctrl+C` ошибки таймаута.

**Почему `db-server` не может скачать пакеты, хотя `web-server` это делает? Что нужно добавить в сеть, чтобы это стало возможно, и при этом `db-server` остался недоступным из интернета?**
У `web-server` есть публичный адрес и маршрут в Internet Gateway, а `db-server` стоит в приватной подсети без публичного адреса и без маршрута наружу. Нужен NAT Gateway в публичной подсети и маршрут `0.0.0.0/0` на него в `private-rt`. NAT пропускает только исходящие соединения, а входящие из интернета не принимает, поэтому база остаётся недоступной снаружи.

### Задание 6. Временный NAT Gateway

![curl checkip](screenshots/task6-db-checkip.png)

`curl https://checkip.amazonaws.com` на `db-server` при работающем NAT Gateway вернул `13.49.61.128`.

![Blackhole](screenshots/task6-route-blackhole.png)

После удаления NAT Gateway маршрут `0.0.0.0/0` в `private-rt` стал `Blackhole`.

![NAT Gateway удалён](screenshots/task6-nat-deleted.png)

Список NAT gateways: `timecapsule-dev-nat-a` в состоянии `Deleted`, его бывший публичный адрес `13.49.61.128`.

**Какой адрес вернула первая команда? Сравните его с Elastic IP NAT Gateway. Почему это не адрес `db-server`?**
Команда вернула `13.49.61.128`, это и есть Elastic IP NAT Gateway. У `db-server` нет публичного адреса, поэтому NAT подменяет адрес отправителя на свой Elastic IP. Все серверы приватной подсети выходят в интернет под одним общим внешним адресом.

**Доступ к базе ограничивают три механизма: отсутствие публичного адреса и маршрута, Security Group `db-sg` и `pg_hba.conf`. Что делает каждый из них? Что произойдёт, если ошибиться только в одном?**
Отсутствие адреса и маршрута делает базу недостижимой из интернета на уровне сети. `db-sg` пропускает порт 5432 только от `web-sg`, а `pg_hba.conf` решает на уровне PostgreSQL, какому пользователю и откуда можно войти в какую базу. Если ошибиться в одном механизме (например, открыть 5432 для всех в `db-sg`), оставшиеся два всё равно защитят базу: из интернета не будет пути, а вход ограничит `pg_hba.conf`.

**Почему PostgreSQL продолжает работать после удаления NAT Gateway? Что придётся сделать, когда на `db-server` понадобится установить обновления безопасности?**
NAT нужен только для исходящего доступа к репозиториям при установке пакетов. Уже установленный PostgreSQL работает локально и во внешней сети не нуждается. Для обновлений безопасности придётся снова временно поднять NAT Gateway (`nat-up.sh`), установить обновления и удалить его (`nat-down.sh`).

### Задание 7. Проверки

![Проверки psql, порта и изоляции](screenshots/task7-checks.png)

`psql` с `web-server` к `db-server` вернул версию PostgreSQL 16.15. Порт 5432 с `web-server` открыт, с `bastion` закрыт. С `db-server` запрос `curl -m 5 https://github.com` завершился таймаутом.

**Почему с `web-server` порт открыт, а с `bastion` нет, хотя оба сервера в одной VPC и маршрут между ними есть?**
Маршрут `local` есть, но его недостаточно: порт 5432 фильтрует Security Group `db-sg`, а она пропускает только трафик от `web-sg`. У bastion другая группа (`bastion-sg`), поэтому пакеты на порт 5432 отбрасываются.

**Почему запрос не проходит? Можно ли из интернета подключиться к порту 5432 `db-server`? Объясните по цепочке из лекции: маршрут, адрес, фильтры.**
Запрос не проходит, потому что у `db-server` нет маршрута в интернет (в `private-rt` только `local`) и нет публичного адреса, которому шлюз мог бы заменить приватный. Из интернета подключиться к порту 5432 нельзя: нет маршрута до подсети, нет публичного адреса, а за ними стоят ещё два фильтра, `db-sg` и `pg_hba.conf`.

![Эксперимент с Network ACL](screenshots/task7-nacl-ssh.png)

Правило 90 (Deny, весь трафик с моего IP) включено: `ssh bastion` завершается `Operation timed out`. После удаления правила SSH снова работает.

![Сайт через VPN](screenshots/task7-site-vpn.png)

Сайт открывается из другого браузера через VPN, то есть с другого внешнего адреса: запрет на мой обычный IP на него не действует.

**Почему заблокировано и SSH, и сайт, хотя вы не меняли ни одной Security Group? Почему с телефона сайт открывается? Почему правило должно иметь номер меньше 100?**
Network ACL фильтрует трафик на границе подсети, раньше, чем он дойдёт до Security Group, и правило 90 запрещает весь входящий трафик с моего адреса, поэтому закрываются и SSH, и HTTP. С телефона в мобильной сети или через VPN внешний адрес другой, поэтому запрет на него не действует. Правила ACL проверяются по возрастанию номера, и применяется первое подошедшее. Правило 100 разрешает весь трафик, поэтому запрет с большим номером никогда бы не сработал.

**Почему Elastic IP нужен `app-server`, но не нужен bastion? Сколько стоит Elastic IP, пока сервер остановлен, и почему? Когда в следующих работах перед сервером появится балансировщик нагрузки, понадобится ли Elastic IP?**
Пользователи заходят на `app-server` по постоянному адресу (`APP_URL`, закладки), а bastion - служебный сервер, его адрес меняется, и достаточно обновить строку `HostName` в `~/.ssh/config`. С балансировщиком Elastic IP на `app-server` не понадобится: пользователи будут приходить на DNS-имя балансировщика.

### Задание 14. Архитектура и решение

## Устные вопросы

**1. Как проходит запрос пользователя от браузера до базы данных? Какие маршруты и какие правила фильтрации он проходит на каждом шаге?**
Запрос приходит на Internet Gateway по маршруту `0.0.0.0/0 → igw` в `public-rt`, затем проходит Network ACL подсети `public-a` и Security Group `web-sg` (порт 80 открыт для всех) и попадает в nginx и PHP-FPM на `app-server`. Приложение узнаёт адрес базы у DNS VPC (`db.timecapsule.internal → 10.17.10.161`) и идёт к нему по локальному маршруту `10.17.0.0/16`. В `private-a` его проверяют Network ACL, `db-sg` (порт 5432 только от `web-sg`) и `pg_hba.conf` (пользователь `timecapsule`, база `timecapsule`, подсеть `public-a`).

**2. Злоумышленник знает приватный IP `db-server`. Что ему нужно получить, чтобы подключиться к базе?**
Сам по себе приватный адрес бесполезен: он не маршрутизируется из интернета. Нужно сначала оказаться внутри VPC на сервере с группой `web-sg` (например, взломав `app-server`), а затем знать пользователя и пароль `timecapsule`. Источник подключения должен быть из подсети `public-a`, как требует `pg_hba.conf`.

**3. Чем временный NAT Gateway лучше постоянного, и какие неудобства он создаёт?**
Временный NAT стоит копейки, а забытый постоянный около $1,25 в сутки, и в остальное время у `db-server` нет выхода в интернет, то есть меньше поверхность атаки. Неудобство в том, что перед каждым обновлением его нужно поднимать (около двух минут) и потом не забыть удалить вместе с Elastic IP. Скрипты `nat-up.sh` и `nat-down.sh` делают это повторяемо.

**4. Как изменится схема, если приложение должно пережить отказ зоны `eu-north-1a`? Каких ресурсов для этого не хватает?**
Сейчас в зоне `a` стоят и `app-server`, и `db-server`, поэтому отказ зоны остановит всё приложение. Нужен второй сервер приложения в зоне `b` и балансировщик нагрузки на обе зоны, реплика базы в `private-b` (или управляемая база с несколькими зонами) с переключением, а также NAT Gateway в каждой зоне для обновлений. Bastion уже стоит в зоне `b`.
